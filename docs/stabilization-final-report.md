# Kikumae Stabilization Gate — 第三者監査・実施報告

作成日: 2026-09-09

## 結論

昨夜の成果には、原文を追加情報で上書きしない修正、ブラウザIncidentを正本にしないサーバー再構築、Safetyの境界ルール、共用端末の消去導線、評価APIの追加認証という実質的な価値がある。一方、証拠付き整理は厳格評価で未達、Phase 3Bの現場耐性も未達である。公開更新はHOLDとする。

## 1. 本当に価値がある成果

- `body_original` の初回原文を追加情報で上書きしない経路を実装した。
- `incident` をクライアントから受け取って保存せず、サーバー側の原文・allowlist intake・Safetyから正本を再構築する経路を追加した。
- Safety GuardをLLMや翻訳より先に実行し、英中韓を含む境界表現を追加した。
- 評価APIを環境ゲートだけでなく管理者認証でも保護した。
- 住民端末の履歴・送信待ち・下書きをまとめて消す導線と送信待ちTTLを追加した。
- 判定を機械可読JSONで保存し、過去の「100%」を無条件に再利用しない資料を追加した。

## 2. 怪しい成果・再検証が必要な成果

- Safetyの372件100%は、93 seedを4 variantに展開した合成開発セットであり、独立した人間ラベル評価でも実災害の保証でもない。実装に近い語彙で構成されているため、数字は強く疑うべきである。
- 以前のPhase 2G evidence 100%は「evidenceが原文のsubstringか」だけの評価で、意味的含意・exact span・source messageの妥当性を検証していない。
- 公開環境ではQwen/Ollamaへ接続できず、公開版がlocal-rules fallbackである点は変わらない。
- Codex Securityの標準スキャンはPython preflight helper不在で完走していない。セキュリティゼロ件とは報告できない。

## 3. 問題の重大度

### Critical

- 現時点で、実証済みのCriticalは確認していない。ただしSafetyを医療判断の代替にしてはならず、直接職員へ知らせる導線を維持する。

### High

- 厳格なEvidence評価で not_found 593/981、token-only 112/981、strict pass 0/170。職員向け項目の一部は原文のexact spanに結び付かず、意味の変形・見落とし検知が弱い。
- Phase 3Bの電源断、DB復元、複数端末競合、実機LAN復帰、ディスク不足、時刻ずれ、長時間稼働が未検証。
- 確認URLはBearer資格情報で、共用端末・スクリーンショット・クリップボード・ブラウザ履歴への残存リスクがある。

### Medium

- Safety評価は合成・派生variant中心で、人間ラベル・実機オフライン・多端末負荷を含まない。
- 会話履歴の一部はクライアント由来であり、職員表示用の補助情報として扱う必要がある。
- 多言語翻訳の意味保存、人間評価、実職員のストレス軽減は未証明。

### Low

- lintの既存警告が12件残っている。
- 既存評価レポートと今回の厳格評価で指標名が揃っておらず、比較時に定義を明示する必要がある。

## 4. 削除・戻すべき変更

今回の監査で、直ちに戻すべき修正はない。Phase 3C以降の新機能・公開更新は戻す／進める対象ではなく、停止する。`body_original` の上書き、client Incidentの信頼、evidenceへの原文prefix代入は再導入禁止。

## 5. 最も重要な発見

1. 「100%」はテスト集合と成功定義を見ないと安全性を意味しない。Safetyは100%でもEvidence strict passは0/170だった。
2. AIの正しさ以前に、クライアント入力をサーバー正本にしていたことと、追加情報で原文が変わり得たことが信頼境界上の根本問題だった。
3. 現在の最大のボトルネックは新しいモデルではなく、現場耐性・証拠の追跡可能性・共用端末の運用である。

## 6. 現在の完成度

評価は **技術プロトタイプ**。限定された匿名合成データでのデモ・人間評価の準備はできるが、「災害訓練可能」「実証可能」「本番利用可能」とは判定しない。

## 7. 次にやること（最大3つ）

1. Evidenceのnot_found項目を人間ラベル付きで再確認し、exact span/source messageを設計する。
2. 原文・Safety・D1・バックアップ・端末キューを対象に、実機を使ったPhase 3Bの残りを小さく実施する。
3. 自治体・避難所運営者へのヒアリングと、限定されたA/B人間評価を行う。効果を「ストレス何%減」とは表現しない。

## 最終判断

ここで新機能開発は止め、人に触ってもらう段階へ移る。ただし公開版や実災害運用ではない。職員・運営経験者による限定評価で「どの情報が足りないか」「整理カードが本当に原文閲覧を減らすか」を測り、その結果で必要な最小修正だけを行うのが合理的である。
