# きくまえ 避難所版 Phase 2D 最終報告

生成日: 2026-09-08

## 結論

Phase 2Dでは、Qwen3.5 4B Incident Extractionを住民フローの必須処理から外しました。

住民の入力は、まずSafety Guardと決定的な構造化処理で即時に職員向けカードへ反映されます。4Bは、情報不足・長文・複数カテゴリ・矛盾・不確実な表現など、追加の意味理解が必要な案件だけを後処理として実行します。

これにより、4Bの完了を待たずに職員が案件を確認でき、住民側の受付・応答も4BのCPU待ちに依存しません。

## 変更点

- `IncidentProvenance`を追加し、各項目に次の出所を保持
  - `user_selection`: 避難者の選択・既知の受付情報
  - `user_text`: 避難者の文章
  - `safety_rule`: 独立Safety Guard
  - `llm_extraction`: 4Bの抽出候補
  - `staff_edit`: 職員修正用の予約値
- 相談ごとに `structuredComplete`、`fourBRequested`、`fourBStatus` を保存
- 4B利用判定を追加し、単純な構造化案件は `not_needed` として即時カード化
- 4Bの同時実行数を既定1、待ち行列上限を既定4に制限
- 待ち行列時間を `modelTimings.queueMs` へ記録
- 住民画面で同一抽出の重複投入を防止し、古い4B結果は新しい入力へ反映しない
- 職員画面のAI整理の先頭に、構造化情報と出所・確認状態を表示
- `questions.structured_incident` へ構造化Incidentと出所を保存する追加マイグレーションを追加
- 固定20件評価、10/20同時利用評価スクリプトを追加

## 処理フロー

```text
住民の文章 / 音声文字起こし
          │
          ├─ Safety Guard（即時・LLM非依存） ──→ 必要なら緊急カード
          │
          └─ 決定的な構造化処理 ──→ 職員カードを先に表示
                                      │
                                      └─ 追加の意味理解が必要な場合だけ4B
```

4Bが停止・タイムアウト・キュー満杯になっても、Safety Guardと決定的なカードは失われません。重要な緊急度の最終確定と住民への返信送信は、引き続き職員確認が必要です。

4B不要の構造化相談を使い、Safety＋カード先行経路とConversationを分けて測定しました。

| 同時数 | カード先行 P50 / P95 | Conversation P50 / P95 | HTTP成功 |
|---:|---:|---:|---:|
| 10 | 596ms / 633ms | 13.4秒 / 20.7秒 | 10/10 |
| 20 | 1.12秒 / 1.13秒 | 16.9秒 / 30.6秒 | 20/20 |

このPCはCPU実行です。Ollama互換APIが提供するキュー時間は今回のConversation負荷試験では取得できず、`queueMs` は未計測です。4Bは同時実行数1、待ち行列4件を上限としています。

ハードウェアはPhase 2A.5/2B監査を引き継ぎ、AMD Ryzen 7 8840U（8コア/16スレッド）、使用可能メモリ約15.27 GiB、AMD Radeon 780M内蔵GPU、OllamaはCPU実行、VRAM計測値0です。今回のPhaseでGPUを新たに有効化していません。

## 障害時の扱い

4B停止のFault Injectionを実行し、次を確認しました。

- 4B停止時も `aiMode=local-rules` へフォールバック
- Safety Guardの緊急フラグを保持
- 相談本文を消失させない
- 住民フローは4B結果待ちにならない
- 古い非同期結果は最新入力へ上書きしない

Phase 2Cで実施済みのOllama停止、Conversation停止、不正JSON、翻訳失敗、音声失敗、ネットワーク障害評価も維持しています。

## 採用しなかった案

- **4Bを全相談に必須化**: CPUで約20〜50秒かかり、住民の受付確認と職員の初動を遅らせるため不採用。
- **Extractionを2Bへ変更**: Phase 2Bで重要事実取りこぼし42.6%だったため不採用。
- **9Bを標準化**: 現在のCPU・RAM・GPU条件では速度と導入リスクを測定し切れておらず、今回のPhaseでは導入しない。
- **4Bのためにプロンプトをさらに短縮**: 速度より原文忠実性・Safety情報保持を優先し、今回の主改善にはしない。
- **AIの候補を最終確定値として扱う**: 人間による最終確認を維持するため不採用。

## 残っている重大リスク

1. 4BはCPU環境で依然として遅く、複雑な相談の詳細抽出は後処理でも数十秒かかります。
2. Conversation 2Bは20人同時でP95約30.6秒となり、音声会話を大量同時利用するには改善余地があります。
3. 現在の公開Web版は避難所内Ollamaへ直接接続できず、公開環境では設定によりlocal-rulesへフォールバックします。
4. Browser Speech APIの認識処理が完全ローカル・外部送信なしであることは未証明です。UIや報告で完全ローカルとは断言しません。
5. ルールによる初期カードは即時性を優先するため、複数カテゴリ相談の主題を完全には表現しない場合があります。4B候補と原文を職員が確認できる構造を維持しています。

## Phase 2Eでやるべきこと

- 住民側の水・物資・トイレ・医療ごとの選択カードを増やし、既知情報を確認済みとして明示する。
- 職員が構造化項目を修正したとき、`staff_edit` として保存し監査ログへ記録する。
- 4Bの非同期ジョブを避難所内Gatewayの永続キューへ移し、再起動後も案件を失わないようにする。
- 複数避難所を想定した4B負荷試験と、キュー遅延・破棄・再試行の運用試験を追加する。
- 音声認識をローカルASRへ差し替える前に、Web Speech APIの通信挙動を実機で確認する。
- 公開Web、避難所LAN、ローカルAI Gateway、復旧後同期の境界をPhase 2Cの比較結果に基づき設計する。
