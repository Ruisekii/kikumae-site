# Kikumae Phase 3B 災害現場耐性評価（最新）

生成日: 2026-09-09

## 判定

Phase 3B Gate は **未達** と判定する。

理由は、AIレーンの簡単な障害では原文とSafety情報を保持できた一方で、電源断、PC再起動、DB再起動、LAN切断復帰、ブラウザクラッシュ、ディスク容量不足、時刻ずれ、バックアップ／復元、複数端末競合をまだ実機または運用構成で検証できていないためである。Gate未達のままPhase 3C以降には進まない。

## 今回の変更

- `app/api/ai/voice/route.ts`
  - Phase 3B評価スイートを追加。
  - AIレーンが使えない場合、`extract` のフォールバック応答にも、入力状態から保持した `originalText` とSafety Guardを含む決定的Incident情報を返すようにした。
  - これはAIの自動判断ではなく、原文とSafety情報を失わないための退避経路。重要案件の最終判断・返信送信は従来どおり職員確認が必要。
- `scripts/phase3b-resilience-eval.mjs`
  - 本番データを書き換えない評価ハーネスを追加。
  - Ollama停止、Conversation停止、Extraction停止、timeout、不正JSON、ネットワーク断を模擬。
  - 通常相談、医療Safety相談、5回の反復、復旧後triage、Safety-onlyを確認。
- `package.json`
  - `npm run eval:phase3b` を追加。
- `app/components/kikumae-client.tsx`
  - 送信前に端末内の送信待ちキューへ保存し、通信復帰時に同じ `submissionKey` で再送する経路を追加。
  - 送信待ちデータには原文、入力内容、Safetyに関係するローカル確認情報を保持する。

- HTTP成功: 12 / 12
- フォールバック表示: 12 / 12
- 原文保持: 12 / 12
- Safety情報保持: 12 / 12
- 医療Safetyの即時フラグ保持: 12 / 12
- 反復5回の原文・Safety保持: 5 / 5
- 障害後の決定的triage復旧: 成功
- Safety-onlyレーン: 成功

### 既存の保持経路

- サーバー側の原文保存列 `body_original`: 実装確認済み
- ブラウザ下書きの保存・復元: 実装確認済み
- 送信失敗時に成功扱いで下書きを消去しない経路: 実装確認済み
- クライアント端末の送信待ちキューと通信復帰時の再送: 実装確認済み（実機LAN断は未実施）

## まだ検証できていない項目

- 停電、PC再起動、Ollama再起動、DB再起動
- LAN切断／復帰、複数端末からの同時利用、同一案件の競合更新
- ブラウザクラッシュからの復元
- ディスク容量不足、時刻ずれ、長時間連続稼働
- DBバックアップ／復元、耐久送信キュー

クライアント端末の送信待ちキューは追加したが、サーバー側の耐久アウトボックス、DBバックアップ／復元、実機LAN復帰試験はまだない。通信断中に保存した相談を復帰後に確実にサーバーへ届ける運用は、実機での確認が必要である。

## Gateに対する結論

「簡単なAI障害で相談原文とSafety情報が失われない」は確認できた。

しかし、Phase 3B全体のGateである「災害現場の簡単な障害で相談原文とSafety情報が失われない」を満たすには、DB永続化、送信待ち、バックアップ／復元、LAN復帰、端末再起動を実際の構成で確認する必要がある。したがって、現時点の判定は **部分通過・Phase 3B継続** とする。

## 次に実装・検証する順番

1. サーバー側の耐久アウトボックスまたは明示的な送信待ち状態を設計する。
2. D1／ローカルDBのバックアップ・復元手順を固定し、原文とSafety情報の復元テストを作る。
3. LAN切断中のクライアントキュー・復帰後再送・重複防止を実機で検証する。
4. PC／DB／Ollama再起動後の再開試験を行う。
5. 10端末相当の同時アクセスと競合更新を確認する。

実務者ヒアリングが未実施のため、Phase 3Cの業務ワークフロー確定には進まない。
