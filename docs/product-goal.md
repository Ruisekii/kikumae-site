# Kikumae Product Goal

この文書では、Kikumaeの目的と手段を分離する。目的は固定するが、AI・整理カード・フォームなどの手段は評価結果によって捨ててもよい。以下の精神的負担軽減に関する記述は、現時点では検証前の仮説であり、達成済みの効果ではない。

## Purpose

**避難所職員が、住民の怒り・焦り・不安・強い要求を含む相談に直接繰り返しさらされることで生じる精神的ストレスを、住民の声・重要情報・Safety・不確実性を失わずに軽減すること。**

Kikumaeが目指すのは、感情を消すことでも、住民の声を弱めることでも、AIで医療・緊急判断を自動化することでもない。職員が必要な情報を安全に受け取り、住民対応を続けられる状態をつくることである。

## Primary User

**避難所で住民対応、相談受付、一次確認、引継ぎを行う職員。**

自治体災害対策本部、保健師・福祉担当、物資担当、施設管理者はSecondary Userまたは引継ぎ先とする。住民は重要な利用者だが、最初に検証するPrimary Userは職員である。

## Core Problem Hypothesis

**避難所職員は、被災者からの怒り・焦り・不安・要求・強い不満などを直接繰り返し受け止めることで、精神的負荷を受ける可能性がある。**

この仮説はまだ未証明である。公的資料から被災自治体職員の負担そのものは支持されるが、住民相談の感情的な受け止めが主要因か、職員の上位課題かは確認できていない。Problem Interviewでは、参加者が自発的に住民対応・苦情・繰り返し要求・強い感情・情報不足・引継ぎを挙げるかを確認する。

## Solution Hypothesis

**住民の原文を保持しながら、事実・要望・経緯・感情・Safety・不確実性を段階的に提示することで、重要情報の把握精度と対応判断を維持しつつ、職員の精神的負担を減らせる可能性がある。**

この仮説は、構造化フォーム、単純LLM要約、Kikumae整理の比較で検証する。Kikumae独自のAI Organizerが必要とは仮定しない。フォーム＋原文保存＋Safety＋職員カードの方が負担を下げるなら、その構成をKikumaeとして採用する。

## North Star

**住民の声と重要情報を失わずに、避難所職員が住民対応による精神的ストレスを軽減し、必要な支援へ対応をつなげられる状態をつくる。**

「把握・引継ぎを速くする」は目的ではなく、精神的負担を安全に軽減するためのOutcome/Mechanismである。精神的負担が下がらないなら、情報把握が速くなってもKikumaeの最終目的は達成していない。

## Primary KPI

**重要情報の把握精度を実用上許容できる範囲に維持した状態での、職員の主観的精神的負担。**

各相談の表示・把握・次の対応判断後に、参加者が回答する1〜5段階の総合尺度をPrimary KPIとする。

1. まったく負担を感じなかった
2. 少し負担を感じた
3. どちらともいえない
4. かなり負担を感じた
5. 非常に強い負担を感じた

職員評価開始前に尺度文言、集計方法、欠損の扱いを固定する。文章を短くしただけの効果と区別するため、読解負担と対応判断負担はSecondary KPIとして別に測る。

暫定Success基準は、D（Kikumae）がA（原文のみ）より総合精神的負担の中央値を**1.0ポイント以上低下**させ、重要情報正答率・Safety・意図/不確実性・対応判断のGuardrailを満たし、BまたはCに対して少なくとも1つの明確な業務上の価値を示すことである。最終的な評価開始前にこの基準を変更しない。

## Guardrails

精神的負担だけを下げるために、情報を隠したり断定したりしない。以下はPrimary KPIと同時に満たす。

1. **重要情報正答率**: 重要事実の正答率95%以上を目標とし、最良の比較条件から3ポイントを超えて低下させない。
2. **Safety見落とし率**: Critical Safetyのfalse negative 0。Safety GuardはLLM停止時も独立して動作し、医療診断や最終トリアージを行わない。
3. **意図・不確実性保持**: 要望、否定、伝聞、可能性、最新訂正、経緯を確定事実へ変形しない。
4. **対応判断精度**: 次に取るべきActionを誤らせる重大な誤り0。AI出力だけで重要な判断を確定しない。
5. **原文・根拠・人間確認**: 原文の消失/改変0、重要主張は原文または明示的な本人入力に遡れる。Human-in-the-loopを維持する。

## Secondary KPI

- 読む時間・対応判断時間
- 原文閲覧率と閲覧理由
- 読解時の精神的負担
- 対応判断時の心理的負担
- 認知負荷、読みやすさ、次の対応の分かりやすさ
- 信頼感1〜5
- 重要情報不足を感じた割合
- 引継ぎのしやすさ
- 住民の受付・進捗確認
- 強い原文へ直接さらされる回数

原文閲覧率は低ければよいとはしない。整理カードだけで安全に対応できた結果として下がったのか、必要な確認を省いた結果なのかを分けて記録する。

## Product Boundary

Kikumaeは、住民と避難所職員の間にある、相談受付・段階的な情報整理・Safety補助・職員の一次遮蔽・引継ぎの薄いレイヤーである。

### Purposeを実現するためのMechanisms

- 刺激の強い原文を毎回直接読まなくても最初の把握ができる段階表示。
- 感情と事実を分け、感情の存在を消さずに表示する。
- 場所、人数、時刻、症状、要望、経緯、不確実性を整理する。
- 必要時だけ原文を開けるEvidence/source導線。
- 受付・確認中・対応中・解決などの状態と引継ぎ。
- 外国語や入力困難な相談の理解補助。ただし原文を正本とする。
- AI停止時もSafetyと原文を残す。

### Human-in-the-loop

重要なSafety、返信、緊急度、FAQ公開、対応完了は職員が確認する。AIの自動返信・自動診断・自動トリアージは目的達成の条件ではない。

### 代替手段を含む構成

比較結果に応じて、次の構成へ縮小できる。

```text
相談
↓
原文保存
↓
構造化フォーム
↓
独立Safety
↓
職員カード
↓
CSV / API Export
```

この構成が最も精神的負担を減らすなら、AIを削除してもKikumaeとして採用する。

## What Kikumae Does NOT Optimize For

Kikumaeは、以下を最上位目標にしない。

- AI利用率
- モデルサイズ、9B化、最新モデル採用
- LLMのJSON成功率だけ
- 機能数、画面数、Phase番号
- 自動化率だけ
- 住民の入力件数だけ
- 文章を短くすることだけ
- 感情を消すこと、怒りを弱めて表示すること
- 職員の感情や人格を採点・監視すること
- 医療診断、生命危険の自動確定、完全な災害判断
- 既存自治体システムの置換
- 完全オフラインを未検証のまま宣伝すること

## 一言説明（検証前の仮案）

**住民の声を消さずに、職員が受け止めやすい形へ。**

これは検証前の説明文であり、「職員のストレスが軽減された」という実証済みの主張ではない。
