# Problem Interview Analysis

## 目的

Problem Interviewの回答を感想集にせず、現場の具体的な業務問題と、Kikumaeの対象範囲を分離して判断する。面談結果が未入力の間は結論を出さない。

## コーディング単位

1. **発言**: 参加者の言葉を短く引用または忠実に要約。
2. **観察事実**: 実際に見た作業・記録・時間。
3. **解釈**: 調査者が考えた意味。発言と混ぜない。
4. **反証**: 現行手段で十分、別の課題だった、頻度が低い等。
5. **重要度**: 頻度×影響を別々に記録。

## 判定ルール

### Problem exists

- 異なる役割または異なる組織で、同じ作業上の問題が複数回現れる。
- 具体的な事例、頻度、影響の少なくとも2つが確認できる。
- 現行 workaround に時間、見落とし、引継ぎの負担がある。
- 文章整理だけで解けると早合点せず、他の制約を分離できる。

### Problem exists but low priority

- 問題は確認できるが、物資、人員、連絡経路、権限等より優先度が低い。
- 発生頻度が低いか、現行 workaround のコストが小さい。

### Problem not found

- 具体例がなく、現行手段が十分である。
- 相談件数が少なく、文章の把握・引継ぎがボトルネックになっていない。

### Different problem found

- 中心課題が、文章ではなく物資不足、人手不足、担当不明、制度・権限、通信・端末などである。
- Kikumaeは問題を解決せず、入力を増やすだけになる可能性がある。

## 集計時の注意

- 「AIがあれば便利」はProblemの実在根拠にしない。
- 製品説明後の肯定反応は、Problem判定と分離する。
- 同じ組織の複数回答を独立証拠として過大評価しない。
- Problemの有無と、DがA〜Cより良いかは別のGateにする。
- ネガティブな回答を除外しない。

## Output

面談終了後に次を作成する。

- 役割別の頻出Problem
- 具体例と反証
- Problem分類の人数ではなく、根拠の強さ
- Kikumaeが触れる範囲/触れない範囲
- A〜D評価へ持ち込むべきケース特性
- Problem不在・低優先・別問題の場合のPivot/Stop案
